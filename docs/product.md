# 제품 개요

## 목표

집에 있는 물건을 **소량** 팔려는 개인이, 팔기 전에 네 가지 질문에 스스로 답하게 돕는다.

1. 내 물건과 조건이 비슷한 상품은 얼마에 올라와 있는가?
2. 확인할 수 있는 판매완료 자료나 매입 견적이 있는가?
3. 업체에 넘기는 것과 개인에게 직접 파는 것 중, 비용을 빼면 각각 얼마가 남는가?
4. 어떤 방법으로 팔고 판매글에는 무엇을 써야 하는가?

가격을 참고해 판매를 **준비**하는 도구다. 매입을 대신하지 않고, 거래 가격을 보장하지 않는다.

## MVP 범위

포함

- ISBN이 있는 전공책·일반 도서 중심. 게임기·전자기기는 모델명과 상태를 직접 입력해 같은 흐름을 사용
- 한국어 UI, 단일 사용자, 로컬 실행, 원화 비교
- API 키 없이 직접 입력·CSV만으로 끝까지 사용 가능

제외 (의도적으로 넣지 않음)

- 계정·결제·판매처 자동 게시·자동 채팅·배송 중개·직접 매입·공개 배포
- 가격 자동 수집(크롤러·스크레이퍼), 사진 업로드, 바코드 카메라 인식
- 게임기·전자기기 자동 식별과 구성품별 가격 보정

## 사용자 흐름

```
물건 등록 → 가격 자료 입력 → 유형별 비교 → 실수령액 계산 → 판매 방법 선택 → 판매글 복사 → 판매 결과 기록
```

## 화면

| 경로 | 화면 | 하는 일 |
|---|---|---|
| `/` | 내 물건 목록 | 검색, 카테고리·상태 필터. 물건마다 가격 자료 건수 또는 "가격 자료 없음", 그리고 다음에 할 일 한 가지(입력된 단계만 보고 정함). **자산 총액은 보여 주지 않는다**(출처·기준이 다른 가격을 더한 숫자는 의미가 없다) |
| `/items/new`, `/items/[id]/edit` | 물건 등록·수정 | 공통 정보 + 도서 전용 정보. ISBN 검증, 서지정보 조회(선택) |
| `/items/[id]` | 물건 상세 | 아래 5단계를 한 화면에서 차례로 진행 |
| `/items/[id]/prices/new`, `…/[priceId]/edit` | 가격 자료 추가·수정 | 유형·금액·출처·확인일·조건 입력 |
| `/triage` | 물건 배분 | 보유 중·판매 중 물건마다 직접 판매 / 업체 / 판단 보류. 시간당 가치 입력, 판단별 건수(금액 합계 없음), 보류 행에는 채울 항목과 상세 화면 링크. 기본 정렬은 보류 먼저, 그다음 시간당 추가 수익 내림차순 |
| `/results` | 판매 결과 돌아보기 | 판매 완료 기록마다 선택 당시 예상(판매금액·실수령액·어림 시간)과 실제 기록의 차이. 요약은 "예상보다 많음/같음/적음/비교 불가" 건수만. 카테고리·고른 방법·판매처별 묶어 보기도 건수만 |
| `/settings` | 설정 | 가져오기 토큰 생성·재발급·폐기, 허용할 브라우저 확장 ID 등록 |
| `/api/import/prices`, `/api/import/items` | 가져오기 API | 토큰과 Origin 검사를 통과한 로컬 도구·확장이 가격 자료를 넣고 물건 목록을 읽음([integrations.md](integrations.md)) |
| `/api/backup` | 백업 다운로드 | DB 파일 전체를 내려받음. 복구는 `pnpm db:restore` |
| `/api/export/all` | 전체 내보내기(JSON) | 현재 모드의 물건·가격 자료·계산·판매 결과를 물건 단위로. 총액 없음, 설정 제외 |

물건 상세의 단계

1. **가격 자료와 비교** — 유형별 묶음, 포함/제외 건수와 제외 사유, 기준 기간 선택, 자료별 포함·제외 전환, CSV 가져오기/내보내기
2. **실수령액 계산** — 업체 판매 / 개인 판매 각각 금액과 비용 입력
3. **판매 방법 선택** — 두 방법의 차액 확인 후 선택 저장(선택 당시 금액을 함께 기록)
4. **판매글 초안** — 입력한 사실로만 만든 제목·본문(항목별, 한 줄) 복사와 글자 수 표시
5. **실제 판매 결과** — 판매처·날짜·금액·비용·시간 기록, 예상과의 차이 확인

## 설계 선택과 이유

- **단계를 한 화면에 모음**: 물건 하나를 놓고 위에서 아래로 내려가면 끝나도록 했다. 화면을 오가며 숫자를 기억할 필요가 없다.
- **판매 방식은 두 가지로 고정**(업체 / 개인): 비교 대상이 명확하고 차액 계산이 단순하다. 판매처별 시나리오는 후속 범위.
- **서버 액션 + 서버 검증**: 폼 검증·가격 집계·유형 제한은 모두 서버에서 한다. 화면에서 보낸 "입력 경로"나 "기준 금액"은 믿지 않고 서버가 다시 정한다.
- **Drizzle + better-sqlite3**: 파일 하나로 백업이 끝나고, 스키마가 타입과 마이그레이션으로 남는다.
- **데모는 같은 DB 안에서 `is_demo`로 격리**: 별도 DB를 두는 것보다 단순하고, 모든 조회가 모드로 범위를 제한하는지 테스트로 확인한다.
- **배분은 물건 하나씩의 판단을 모은 것**: 물건 상세에서 저장한 업체·직접 판매 계산을 그대로 다시 쓰고, 새 계산을 만들지 않는다. 판단 기준인 시간당 가치는 사용자가 정한다. 앱이 정하면 그 숫자가 판단을 대신하게 된다.
- **시간당 가치는 `user_settings` 테이블에 모드별 한 행**: 데모에서 입력한 값이 실제 판단에 섞이지 않는다. 데모 초기화 때 데모 값도 지운다.
- **돌아보기는 건수만 요약**: 물건마다 기준 금액·비용 항목이 달라 차액을 더한 숫자는 해석하기 어렵다. 실제 비용을 "모름"으로 남긴 기록은 0원으로 치지 않고 "비교 불가"로 센다.
- **복구는 화면이 아니라 스크립트로**: 실행 중인 앱이 DB 파일을 열고 있어 화면에서 파일을 바꾸면 반쯤 바뀐 상태가 될 수 있다. 앱을 끈 뒤 검증·안전 사본·교체를 한 번에 하는 스크립트로 했다.
- **도서 상태 세부(필기·밑줄·파손·부록)는 있음/없음/모름**: "모름"이면 판매글에 쓰지 않는다. 체크박스였다면 "체크 안 함"이 "없음"으로 읽혀 사실이 아닌 문장이 만들어진다.
